> total time

is caused by:

# Approach 2

# Approach 3

## Claude's Findings

**Short version:**
- **At this file's size (~650 KB), none of the approaches causes jank** on a laptop. `JSON.parse` takes 1–2 ms. Pick by architecture, not speed.
- **`response.json()` is not parsed off the main thread.** It's the slowest main-thread option.
- **A worker doesn't remove the main-thread cost.** Getting the object back to the page costs about what `JSON.parse` does, whether it comes by `postMessage` or through IndexedDB.
- **What a worker plus IndexedDB does buy** is a faster *repeat* visit, since it skips the network.
- **The real fix for large data** is not bringing all of it to the main thread.

### The experiment

[`demo/benchmark/json/`](../demo/benchmark/json/) has one page per approach, plus a baseline page that loads no data:

| Page | Approach |
|---|---|
| `fetch-json.html` | **1.** `fetch` + `response.json()` |
| `fetch-text.html` | **1b.** `fetch` + `text()` + `JSON.parse`, to see whether `json()` parses off the main thread |
| `embedded.html` | **2.** The JSON in a `<script type="application/json">` (`<` escaped), then `JSON.parse`. Generated by `embed.mjs`. |
| `worker-clone.html` | **3a.** A worker fetches and parses, then posts the object back (structured clone) |
| `worker-idb.html` | **3b.** A worker fetches, parses and stores in IndexedDB, and the page reads it back. `?warm` measures the read alone, as on a repeat visit. |
| `baseline.html` | The same page with no data: what page startup alone costs |

**Each page measures:**
- **ready:** when the data is usable, in ms since navigation start;
- **step:** the main thread's own part (for 1, the whole `fetch` + `json()`, network wait included);
- **frame gap:** the longest gap between animation frames, i.e. jank, in every browser;
- **longest task and blocking time:** from the Long Tasks API, Chromium only.

**How it ran:**
- **`run.mjs`** opens every page in a **fresh browser context** each run (empty cache and IndexedDB, top-level navigation, not an iframe), in Chromium, Firefox and WebKit, and prints medians of 11 runs.
- **Two data sizes:** the file itself, and a ten-times-larger copy (6.3 MB, `modules` repeated, generated by `embed.mjs`).
- **Throttled runs:** Chromium also ran with its CPU 4× slower, roughly a mid-range phone; the others can't be throttled.

```
node demo/benchmark/json/run.mjs [baseURL] [runs] [shoelace | shoelace-x10] [cpu-throttle]
```

### What the numbers say

**1. Is `response.json()` parsed off the main thread? No.**
- **The main-thread cost is there:** with the CPU throttled and the big file, `json()` produces an **89 ms long task** on the main thread, while `text()` + `JSON.parse` stays under the 50 ms long-task threshold. And `json()`'s step is the slowest in every run.
- **The spec agrees:** it parses the bytes on the page's thread once the body has arrived; reading the body is what happens in the background.
- **If anything,** `text()` + `JSON.parse` is slightly better: it splits the work into two smaller tasks.

**2. Embedding** is about as fast as fetching at 650 KB, and parsing is just as cheap (it's the same `JSON.parse`).
- **Its cost is elsewhere:** the HTML itself gets bigger. At 6.3 MB, the embedded page was ready last in Chromium (394 ms throttled), because the parser has to read the whole JSON text as HTML first.
- **On a real network,** everything after the `<script>` waits for it to download.
- **What it saves** is a round trip (no second request), which local tests can't show. It's also the natural partner of o2h's `embed` option: the data is guaranteed to be the snapshot the HTML was rendered from.

**3. A worker doesn't take the cost off the main thread.**
- **Approach 3a:** the parse moves to the worker, but the object has to come back. Structured-clone deserialization on the main thread costs about what `JSON.parse` does (Chromium, 6.3 MB: 10.5 ms vs 9 ms; throttled: a 51 ms long task). Worker startup also makes the data later.
- **Approach 3b:** reading from IndexedDB is also a structured-clone deserialization on the main thread. It's not cheaper than parsing, and in Firefox it's much slower (24 ms vs 1 ms at 650 KB; 50 ms vs 13 ms at 6.3 MB).
- **What 3b warm does win is time:** a repeat visit skips the network, so the data is ready soonest (Chromium: 10 ms vs 24, throttled 36 vs 131). It isn't less jank, though. The trade-offs: cache invalidation, storage, and Firefox's slow reads.

**4. Where jank starts:**
- **On a laptop:** not at 650 KB, nor really at 6.3 MB. There were no long tasks in Chromium, with frame gaps up to ~45 ms in WebKit.
- **On a slower CPU:** a few MB is where single tasks pass 50–90 ms.

### Recommendation

- **For this file:** use whichever fits the architecture. With o2h (server-rendered HTML), **embed** it (or use o2h's planned `embed` option): one request, and a guaranteed matching snapshot. Without server rendering, **fetch** it, with `text()` + `JSON.parse` rather than `json()`. Neither janks.
- **For repeat visits:** an IndexedDB cache (3b) makes the data available sooner, especially in Chromium. It's a caching decision, not a jank fix.
- **For large data (MBs):** the only real cure for jank is **not bringing all of it to the main thread.** Keep it in the worker, and send the page only what it shows: a projection of the data, or, with o2h, the **HTML itself**. o2h runs in a worker and returns a string, which the page assigns with `innerHTML`. Nothing JSON-sized is parsed or deserialized on the main thread. That's a natural next experiment: approach 3c, "worker fetches, parses and renders with o2h", if you'd like it measured.

### Caveats

- **Local server:** network latency and bandwidth are effectively zero. On a real connection, transfer time dominates `fetch` and embedding alike, and the differences above shrink relative to it.
- **Only Chromium can be throttled** and has the Long Tasks API. Firefox's and WebKit's timers are 1 ms coarse, so their small numbers are rough.
- **Headless browsers,** with medians of 11 runs.

## Claude's Answer II

### What factor matches a ~$100 Android?

**Roughly 10× on your machine, with 20× as a reasonable worst case for the cheapest Androids.** Here's how I get there; treat the benchmark figures as approximate, from memory of published results.

- **Your laptop:** a current Core Ultra 9 scores around **3,000** single-core in Geekbench 6.
- **Phones, by price:**

| Phone class | Typical chips | Geekbench 6 single-core (approx.) | Ratio to your laptop | Suggested throttle |
|---|---|---|---|---|
| Budget, ~$150–200 | Snapdragon 4 Gen 2, Helio G99 | 700–900 | 3.5–4.5× | **5–6×** |
| **~$100** | Helio G85 / G36, Unisoc T606 / T615 | 350–450 | 7–9× | **10–12×** |
| Android Go, < $80 | Helio A22, Unisoc SC9863A | 150–250 | 12–20× | **15–25×** |
| KaiOS feature phones | Snapdragon 205, Unisoc T107 / T117 | ~100 or less | 30×+ | (see below) |

- **Why I round up from the raw ratio:** cheap phones are worse at running a browser than their CPU score suggests. They have smaller caches, slower memory, fewer fast cores (the renderer can land on a slow one), and they throttle when warm. Real-world JavaScript benchmarks such as Speedometer usually show a wider gap than single-core CPU scores.
- **What DevTools throttling doesn't model:** memory pressure and garbage collection, slow storage (which matters for IndexedDB), the network, or the phone's GPU. I'm also not certain that Chromium slows a page's workers as much as its main thread. If it doesn't, the worker rows look better than they would on a phone.

**To calibrate instead of estimating:**
- **Lighthouse:** it reports a `benchmarkIndex` for the machine it runs on (in the JSON report, under `environment`), and its throttling documentation explains how to pick a CPU multiplier from it for a target device class.
- **A real phone is the most reliable check.** A ~$100 Android over USB with `chrome://inspect` (remote debugging) runs these benchmark pages as they are, since each page prints its own results. It's a one-time cost that settles every "what factor?" question.

**About "feature phones":** if you mean KaiOS phones (JioPhone and the like) rather than cheap Androids, speed isn't the first problem. Their browsers are old engines. KaiOS 2.5 is Gecko 48, with no ES modules. KaiOS 3 is Gecko 84, with no top-level `await` and no `Object.hasOwn`. assign-gingerly and o2h's client side wouldn't run there without a build step that targets those engines. Cheap Androids run current Chrome, so they're the realistic low end for this package as it is.

### Your 20× observation: embedding delays the first paint

I reran at 20×, and added **first contentful paint** to the harness (`firstPaint`, also in `run.mjs`'s output), since that's what the embed costs:

| Chromium, CPU 20× slower, ~650 KB | Data ready | Longest frame gap | **First paint** |
|---|---|---|---|
| 0 baseline (no data) | 1,501 | 917 | 1,472 |
| 1 `fetch` + `json()` | 2,312 | 883 | 1,384 |
| 1b `fetch` + `text()` + `JSON.parse` | 2,277 | 883 | 1,380 |
| **2 embedded + `JSON.parse`** | **2,147** | **1,167** | **1,948** |
| 3a worker, posted back | 2,393 | 900 | 1,404 |
| 3b worker → IndexedDB, cold | 2,598 | 900 | 1,404 |

(Medians of 7 runs, in ms. The warm IndexedDB row isn't shown: it's a second navigation in the same browser context, with its code already cached, so its startup isn't comparable.)

- **Page startup dominates at 20×:** even the baseline page, with no data, has a ~900 ms frame gap.
- **Embedding adds about 250 ms of frame gap** on top of that (1,167 vs ~890). More importantly, it **delays the first paint by about 560 ms** (1,948 vs ~1,390). The HTML parser has to work through the whole JSON text before the browser can paint, even though the content comes before it in the page.
- **In exchange, embedding has the data first** (2,147 vs 2,277–2,598), because it needs no second request.
- **Fetch and worker look alike:** the page paints first, then the data arrives. Their frame gaps match the baseline's, so the JSON adds no visible jank at this size, even at 20×.

So your reading is right, with this nuance: embedding trades **a later first paint** for **earlier data**. For a page that should show content quickly on a slow phone, fetching after the first paint is better.

**On a real network, the embed's penalty is partly hidden,** if the server **streams** the page and puts the JSON at the **end of the body**. The content arrives and paints before the JSON bytes do. Locally the whole file arrives at once, so the parser meets the JSON immediately. That's worth keeping in mind for o2h's `embed` option: write the data after the rendered HTML, never before it, and keep it to what the client needs.
